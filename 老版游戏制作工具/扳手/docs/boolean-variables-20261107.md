`0x4109E6` 的命令派发保存并传递当前脚本对象；指令表把 `0x05` 条件判断导向 `0x41179F`、把 `0x0B` 赋值导向 `0x401925`，分别调用上述 reader/writer。`0x0A` 的实现 `0x415ACA` 只清除编号 `0..255`，证明局部清除域，不能据此推导整个布尔区容量。

## 容量纠错与本版政策

`0x413207` 按人物编号读取 `DWORD[0x4930C8+id*4]`；`0x412265` 也把 `0x4930C8` 作为独立数组初始化地址。布尔编号 2048 的计算结果正好等于该地址。旧 512 字节范围 `0x492FC8..0x4931C7` 因而包含人物字段。

原生 reader/writer 和条件／赋值解析路径没有证明 4096 或 2048 是合法 BOOL 数量。`0x418830` 复制 `this+0x38` 起的 `0x2000` 字节，是包含其他状态的混合块，不能解释为 65536 个 BOOL。

本版采用明确的工具政策：默认 `0..1535` 可读写，`1536..2047` 仅作只读保留域，`>=2048` 不在普通 BOOL 列表展示且保存入口拒绝。默认可写域依据本地剧本资料的局部 `0..255`／全局 `256..1535` 描述保守选择；**1536 是本工具的默认可写数量，不是已证实的原生容量。** 保留域也不被命名为已确认的布尔变量。

保存始终从只读编号和当前布局重新计算地址与掩码，不信任表格中的地址文本；写入只修改目标位。显示必须包含位号／掩码，让相同字节地址下的各行可区分。

## 旧证据作废

- 旧 `variables_bool_anchor` 命中的 `0x402442` 是把 `0x492F38` 传入文本绘制路径。对其加 `0x90` 恰好得到正确数据首址，不构成 BOOL 寻址证据。
- 旧 `variables_bool_storage` 命中的 `0x403766` 是像素尺寸向上取整辅助函数；`0x4279DB/0x4279EB` 的调用属于画面裁剪／绘制，不能证明 BOOL 存储或容量。
- 以真实 reader、writer、除 8 调用、掩码表、脚本对象实参及人物数组重叠证据替换这两条旧证据。旧模拟测试只证明实现自洽，不能据此宣称 4096 位是真实布局。
